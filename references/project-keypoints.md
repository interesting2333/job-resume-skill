# 项目关键点总结

## 目标

把工程代码、用户提示、README、项目描述或零散材料，提炼成求职可用的项目资产：

- 一句话项目定位
- 业务/用户价值
- 技术架构和关键模块
- 技术难点与方案权衡
- 可写进简历的 bullet
- 面试官可能追问的问题
- 还需要补充的事实和数据

## 输入类型

### 工程目录

先用工具盘点工程，再读关键文件。优先读取：

- README、docs、架构文档、接口文档
- `package.json`、`pom.xml`、`build.gradle`、`go.mod`、`pyproject.toml`、`requirements.txt`、`Cargo.toml`
- Dockerfile、compose、Kubernetes、CI 配置
- 入口文件、路由、controller、service、model、schema、migration、配置文件
- 测试目录和性能/压测脚本

推荐先运行：

```bash
python scripts/project_inventory.py path/to/project
```

再根据盘点结果读取最关键文件。不要试图一次性读完整个工程。

### 提示词或项目描述

如果用户只给提示或描述，直接做结构化提炼，但要区分：

- 已明确事实：可以写进项目总结
- 合理推断：必须标注“推断”
- 缺失信息：列入待补充问题

### 简历里的项目段落

先还原项目上下文，再提炼亮点。重点判断当前写法是否缺少产物、结果、复杂度或个人贡献。

## 分析顺序

1. 项目定位：
   - 这是给谁用的
   - 解决什么问题
   - 属于业务系统、基础设施、工具平台、数据/AI、前端应用、移动端、插件还是自动化项目

2. 技术栈：
   - 主要语言、框架、数据库、中间件、部署方式
   - 工程化、测试、监控、CI/CD、权限、安全、性能相关能力

3. 核心模块：
   - 用户/权限
   - 数据模型
   - 业务流程
   - 接口/任务/消息/调度
   - 前端交互
   - 部署和运维

4. 关键难点：
   - 性能、并发、稳定性、一致性、数据量、权限、安全、可观测性、扩展性、兼容性
   - 如果代码里看不出难点，不要硬造。改为列出“可追问用户确认的难点”。

5. 求职价值：
   - 这个项目能证明候选人的什么能力
   - 对目标岗位最有价值的部分是什么
   - 哪些内容应该写进简历，哪些只是技术细节

## 输出格式

```markdown
# 项目关键点总结

## 一句话项目定位
[用一句话说清：这是一个面向谁、解决什么问题、用什么方式实现的项目]

## 核心价值
- 业务价值：
- 用户价值：
- 技术价值：

## 技术栈与架构
- 技术栈：
- 关键模块：
- 数据/接口/部署：

## 项目亮点
1. [亮点]
   - 证据：
   - 可写进简历的角度：

## 可写进简历的 bullet
- [问题/目标] + [动作] + [产物] + [结果/待补指标]

## 面试官可能追问
- 问题：
  - 为什么会问：
  - 建议准备：

## 待补充信息
- [需要用户补充的数据、角色边界、结果、难点]
```

## 简历 bullet 生成规则

优先使用：

```text
为了解决[问题/目标]，设计/实现/重构[产物或模块]，通过[关键技术/方法]，实现[结果]。
```

如果缺少结果：

```text
为了解决[问题/目标]，设计/实现[产物或模块]，覆盖[使用对象/流程]，[量化结果待补]。
```

## 面试对抗提炼

每个项目至少生成 5 类追问：

- 项目背景：为什么要做，解决谁的问题
- 技术方案：为什么这样设计，有什么备选方案
- 个人贡献：你负责哪部分，边界是什么
- 结果证明：怎么衡量效果，有没有数据
- 复盘改进：如果重做，会怎么优化

## 不要做

- 不要把工程里存在的依赖都写成项目亮点。
- 不要把 CRUD 项目包装成高并发核心系统，除非有真实证据。
- 不要根据目录名脑补业务规模。
- 不要把团队成果全部写成个人主导。
- 不要忽略用户的目标岗位；同一项目面向后端、前端、产品、测试、运维的提炼角度不同。
